# DECISIONS

Running log of engineering decisions that deviate from, refine, or instantiate the
package specification. Precedence rule from `01_MASTER_CODEX_PROMPT.md`: **leakage
prevention + honest reporting + hardware constraints** outrank convenience.

## D001 — Measured hardware differs from the specification's assumption (2026-10-08)

Spec `02_IMPLEMENTATION/00_VPS_24GB_SETUP.md` assumes ≥32 GB RAM and 100–150 GB SSD.
Measured reality on this VPS:

| Resource | Spec assumption | Measured |
|---|---|---|
| GPU | 1× NVIDIA 24 GB | NVIDIA **L4**, 23034 MiB (22.5 GiB) usable |
| System RAM | recommended ≥32 GB | **15 GiB** total (~13 GiB available) |
| CPU | not specified | **4 cores** |
| Free disk | 100–150 GB recommended | **~54 GB** free |

**Consequence:** the spec's own fallback clause applies — "Nếu thấp phải chạy chế độ
compact" (run in compact mode). We therefore:
1. Never hold two large models resident simultaneously (E5 / XLM-R / Laya are loaded,
   used and unloaded phase-by-phase, per the spec's memory-safe schedule).
2. Cap dataset profiles conservatively and treat `full` as opportunistic.
3. Must serialise: no concurrent reader-training + embedding build.

The L4 is compute capability 8.9 (Ada) — bf16 is supported. The spec's "24 GB GPU"
assumption is satisfied for VRAM; the RAM/disk gap is the binding constraint.

## D006 — Negative-audit ambiguity counts distractor documents only (2026-10-08)

Spec `01_SPECIFICATIONS/04_DATASET_VALIDITY_AND_LEAKAGE.md` §6 requires ambiguous
negatives to be flagged (not dropped) and their counts reported openly. The P1 heuristic
(`src/data/auditor.py`) originally counted `lexical_coverage>=0.70`, `reader_proxy>=0.80`
and a plausible-answer hit on *every* corpus document — including the question's own gold
doc. For a SQuAD2-style negative the gold doc is *expected* to overlap the question and
hold its plausible answers, so the audit flagged essentially every negative and the flag
became useless for the trainer. Measured on the HEAD run (pilot profile, cap 100/split):
95/95 pilot negatives flagged (rate 1.000; train 33/33, val 29/29, test 33/33), all 95
with gold-doc signals; smoke 20/20.

**Decision.** Ambiguity is counted on **distractor documents only** — corpus documents
other than the question's `gold_doc_id`. Signals on the gold doc are reported as an
informational count and are *never* ambiguity. The plausible-answer matcher also changed
from raw substring to token-sequence matching: on the pilot distractor hits, 30 substring
hits included 16 fragment matches ("ba" inside "bàn", "Hạ" inside "hạn"), i.e. 14 real
hits — token matching keeps those 14 and drops the fragments.

**Thresholds (judged on measured pilot data, train/val only — never on `test_strict`).**
`lexical_coverage>=0.70` and `reader_proxy>=0.80` kept: across 1140 distractor documents
none reaches either threshold (distractor coverage p50 0.10 / p90 0.29; reader proxy p50
0.07 / p90 0.17), while gold docs sit at coverage p50 0.75 / p90 1.00 — the thresholds
cleanly separate the two sides. Sensitivity grid (cov 0.5/0.6/0.7/0.8/0.9 × proxy
0.7/0.8/0.9): flagged counts per split go 5/2/10 → 2/2/4 → 1/1/4 and stay flat for every
cov >= 0.70; proxy moves nothing. At 0.70/0.80 all pilot flags come from
plausible-answer-in-distractor (14 hits), none from the lexical thresholds.

**Before/after (real runs, pilot profile, 95 negatives; test shown for transparency only):**

| split | negatives | flagged before (any doc incl. gold) | flagged after (distractors only) | gold-doc signals (informational) |
|---|---|---|---|---|
| train_strict | 33 | 33 (rate 1.000) | 1 (0.030) | 33 |
| val_strict | 29 | 29 (1.000) | 1 (0.034) | 29 |
| test_strict | 33 | 33 (1.000) | 4 (0.121) | 33 |
| all | 95 | 95 (1.000) | 6 (0.063) | 95 |

Smoke profile: 20/20 → 0/20. The heuristic is applied identically to all splits.

**Plumbing (spec §6 policy).** The flag travels with the artifacts:
`questions_{split}_strict.parquet.ambiguous_negative` (False for answerable rows),
`difficulty.ambiguous_negative` on every scenario, and
`data/processed/ambiguous_negatives.json` (`flagged_qids` + counts per strict split; note:
"automated heuristic only; no human review"). The primary RL trainer skips flagged
*train_strict* negatives from reward-bearing updates; val/test keep their flags so clean
vs ambiguous negatives can be compared. Flagged counts are reported in
`schema_report.md`, not hidden. Scenarios were also moved to
`data/scenarios/scenarios_{train,val,test}.jsonl` (`cfg['paths']['data_scenarios']`) — the
layout `src.data.artifacts` already reads — and the stale `data/processed/scenarios_*.jsonl`
copies were removed.

The flag is an automated heuristic; no human review was performed, and this is stated in
the CSV, the report and the JSON alike.

## D007 — Laya base checkpoint resolution and the teacher JSONL row schema (2026-10-08)

Resolves D003. The base is `convaiinnovations/laya-multilingual` (the 4-way `next_action`
checkpoint on `jhu-clsp/mmBERT-base`, ~322M parameters), not `convaiinnovations/laya` (the
`laya-train` CLI default) and not the spec's shorthand `multilingual`. `--base` accepts a
local directory, so training never depends on Hub resolution at run time. The revision is
resolved at run time, in this order (`src/pipeline/train_laya.resolve_revision`): a local
directory needs none; an explicit `laya.revision` wins; otherwise the reviewed SHA for the
repo id is read from `laya.revisions.PINNED_REVISIONS` **as installed** (never copied into
source, so an upstream re-pin is picked up); otherwise the Hub commit SHA is queried with
`HfApi().model_info(...).sha` and recorded. The snapshot is materialized with
`snapshot_download(revision=..., allow_patterns=[rl_agent_config.json, model.safetensors,
tokenizer/*, encoder/*])` and that local directory is what `--base` receives. Every run
manifest records the base id, the revision, how it was chosen (`revision_source`: local |
explicit | pinned | queried) and the SHA256 of the identity files (`model.safetensors`,
`rl_agent_config.json`, `encoder/config.json`, `tokenizer/tokenizer.json`;
`tokenizer/tokenizer_config.json` is excluded because the library repairs it in place on
first load). The same repair is applied to the output checkpoint before hashing
(`train_laya.normalize_checkpoint`), so the hash every run manifest records is the one later
loads and P6 cache stamps see. At the currently pinned revision the resolved SHA is
`e4e9ddf21a7b1903b7acffd8814ad4307bf63a67`. The configured `max_len=768` /
`head_max_len=192` override the base's own 1024/256, i.e. training runs on shorter inputs
than the published checkpoint; the saved checkpoint carries the budgets training used.

The teacher file (`make_teacher`) is the `{state, questions, gold}` JSONL that
`laya.train.finetune` reads: one row per reachable decision state, sorted by (qid,
history):

    {"state": <state_text.serialize_state(obs)>,         # the exact text a rollout feeds Laya
     "questions": {"next_action": {"type": "choice", "instructions": ..., "criteria": {4}}},
     "expected": {"next_action": "<argmax>"},            # hard label, always present
     "gold": {"next_action": {"probabilities": {...}}},  # soft target; absent in hard mode
     "meta": {qid, split, scenario_id, difficulty, privileged, state_hash, env_state_hash,
              state_text_version, history, depth, valid_actions, expected, ambiguous,
              teacher_mode, teacher_temperature}}

Masked actions carry exactly 0.0 mass and the soft target sums to 1. `val_strict` rows are
privileged hindsight (diagnostic only, never fit): they carry `meta.privileged = true` and
their file is named `laya_val_diagnostic.jsonl` so it cannot be mistaken for training data.
`laya-train`'s temperature calibration split (`calib_max=400, calib_frac=0.1,
calib_seed=20260922`) is `TrainConfig`-only, so P5 trains in-process and records the
equivalent CLI command together with the caveat that a CLI rerun is only equivalent while
those values hold. `laya` 0.4.0 `finetune` writes no optimizer/scheduler state and always
starts from epoch 0: resume is recorded as unsupported (spec 06 §5) and a rerun over an
existing checkpoint is refused unless `--force`.

## D008 — P3 threshold selection, hard acceptance gate, profile scale, and bf16 training (2026-10-08)

The first pilot reader was unusable and the pipeline reported success anyway. Two defects,
reproducible from the cap-100 pilot artifacts:

1. **Selection objective.** `src/qa/postprocess.sweep_threshold` sorted the 33-point grid by
   `(-em_overall, -f1_overall, threshold)`. Overall EM/F1 score an impossible question against
   an empty reference, so an always-null reader scores `em_overall` = the impossible share
   (0.29 on val) and beats every answering threshold (<= 0.06); the sweep therefore selected
   threshold -8.0 — the all-null row — in every run. SQuAD2 never uses overall EM to pick the
   threshold (answerable and impossible metrics are reported separately), and
   `03_EXPERIMENTS/01_METRICS_...md` §2 (line 30) says the two definitions must be reported
   apart, not mixed. The docstring claimed the opposite; it now states the real rule and why
   overall EM is invalid on an impossible-heavy val set.
2. **Unenforced acceptance.** `src/pipeline/train_reader.acceptance` recorded
   `non_empty_span_with_valid_offset: {passed: false, example: null}` and the run was still
   registered SUCCEEDED, with its `reader_inference.json` frozen for P4. Spec 02 §10 makes
   that check part of P3's acceptance.

**Selection rule (feasible-first).** Among thresholds that satisfy §10's constraint (>= 1
non-empty span with valid provenance at that threshold), `choose_best_threshold` now picks the
highest `f1_answerable + no_answer_accuracy`; ties go to higher `em_answerable`, then to the
lower threshold. A sweep in which no threshold answers raises and the run fails, instead of
shipping an abstain-always reader. Sweep rows keep every per-threshold metric and gain two
audit fields (`acceptance_constraint_met`, `selection_objective`); `reader_eval.json` gains
`threshold_selection` (`objective`, `constraint`, `chosen_threshold`,
`n_feasible_thresholds` of `n_thresholds`, `objective_only_threshold`, `constraint_binding`)
and the CLI prints it, so both the constraint and whether it decided the pick are visible.
`src/pipeline/train_correctness.py` (fold readers) shares `choose_best_threshold` and inherits
the rule — including the raise; an infeasible fold sweep should be treated as a failed fold.
A `SELECTION_FAILED` `reader_eval.json` with the sweep is kept as evidence in that case.

**Hard acceptance gate.** `require_acceptance` raises before `reader_inference.json` is
written when the span check fails; the exception lands in the existing FAILED path (registry
FAILED, no frozen contract for a rejected reader), while `reader_eval.json` and the
predictions parquet stay on disk as evidence.

**Scale and epochs.** Pilot caps align with `06_PIPELINE_ORCHESTRATION_AND_RESUME.md` §3:
`smoke: 20 -> 40`, `pilot: 100 -> 300` (`small`/`medium`/`full` unchanged). Reader epochs scale
per profile through the overlays — `configs/pilot.yaml` 30, `configs/medium.yaml` 3, base
(full) 2 — because 300 questions at the full-profile default of 2 epochs give 6 optimizer
steps. Regenerated pilot P1/P2 at cap 300: 300 scenarios/split, BM25 recall@1 0.9789, union
recall@5 0.9984, unreachable 0.0033 — the data and retrieval are sound, so the weak reader is
not a retrieval artifact.

**bf16 training (pilot/medium).** The fp16 gate/training logs on this L4 carry `grad_norm:
inf` (4 of 40 gate steps, and again in the 60-step run): the fp16 scaler reported inf gradients
and skipped those steps. bf16 is native on Ada (D001) and needs no loss scaling: the same gate
re-run under bf16 (`reader.bf16: true`) logged 0 inf in 40 steps, and the 270-step pilot run
logged 0 inf. `reader.bf16: true` is set in the pilot/medium overlays only; base profiles keep
`fp16: true` and inference keeps `src.qa.infer`'s fp16 autocast path (contract unchanged).

**Measured before/after (pilot, val_strict: 212 answerable / 88 impossible):**

| | before: cap 100, 2 epochs (104 windows, 6 steps) | after: cap 300, 30 epochs (316 windows, 270 steps, final loss 0.442, bf16) |
|---|---|---|
| selected threshold | -8.0 (all-null) | -8.0 |
| answered answerable | 0 / 71 | 7 / 212 |
| f1_answerable | 0.0 | 0.0113 |
| no_answer_accuracy | 1.0 | 0.9659 |
| acceptance | span check passed=false, run SUCCEEDED | 4/4 checks pass, run SUCCEEDED |

A 20-epoch overlay run at cap 100 (60 steps) already showed the grid *can* answer — at 8.0 all
71 answerable questions were answered (f1_answerable 0.113, no_answer_accuracy 0.035) — while
the `em_overall` sort still picked the all-null row: the selection bug alone hid it.

**Honest outcome at pilot scale.** Threshold -8.0 is also the objective's own argmax
(`constraint_binding: false`): with these predictions `no_answer_accuracy` spans 0.97 -> 0.01
while `f1_answerable` never exceeds 0.1604, so any sum of the two rewards abstention. The
reason is visible in the margins: answerable (median -2.51, IQR -4.88..+0.33) and impossible
(median -2.87, IQR -5.19..-0.02) overlap almost completely — this reader has learned no
null/answer discrimination (at 0.0 it answers 151/212 answerable but also 66/88 impossible).
The plumbing is now honest and the checks pass truthfully, but reader quality at pilot scale is
the open problem, and the objective is structurally abstention-biased whenever `f1_answerable`
is small. A follow-up decision should either constrain the selection (e.g. a minimum answer
rate or a false-answer budget) or improve the reader's training — not let the raw sum decide.
Nothing was retuned to make the numbers look better: the grid is base.yaml's, unchanged.

**Tests.** `tests/test_reader.py` + `tests/test_reader_pipeline.py` cover: a null-spam row
cannot win a feasible sweep, a binding constraint is flagged, an infeasible sweep fails the
run, and the hard gate raises and withholds the contract. Committed subset: 152 passed,
1 skipped.

## D009 — laya 0.4.0 CUDA fine-tuning: the pre-training calibration pass (2026-10-08)

**Defect.** The pinned `laya` 0.4.0 cannot fine-tune on CUDA. In `laya/train.py`, `finetune`
scores the eval items with `calibration_records(model, tok, eval_items, dev, ...)` (line
1086) before `train_model`, whose `model.to(device)` (line 638) is the first place the model
is moved. `calibration_records` (defined line 709) sends every batch to `dev` through
`_forward` (line 607, called line 718) while the encoder is still on cpu (`load_checkpoint`
returns it there), so a `--device cuda` run dies before the first optimizer step:

    RuntimeError: Expected all tensors to be on the same device, but got index is on cuda:0,
    different from other tensors on cpu (when checking argument in method
    wrapper_CUDA__index_select)

Every normal run hits it: the pre-train check runs whenever there are eval items, and with
no `--eval` file the eval set defaults to the calibration slice (`n_calib = min(calib_max,
int(len(items) * calib_frac))`, at least one item for any 10+ item dataset). Reproduced with
the library API alone and by the vendor `laya-train` CLI, which calls the same `finetune`;
the failing run is `p5-laya-ce-smoke-2026-10-08T142044+0000` (FAILED) in
`outputs/runs/index.jsonl` with exactly that message.

**Fix, and why it lives in our code.** `train_laya.patch_calibration_records`
(`src/pipeline/train_laya.py:99`, applied at the `finetune` call site) wraps
`laya.train.calibration_records` in-process: the wrapper runs `model.to(device)` and then
delegates the call unchanged. Site-packages is never edited — `laya` 0.4.0 is the reviewed
pin every run manifest records under `library_versions`, and a patched installed tree would
silently diverge from what a reinstall, a reviewer, or the recorded `equivalent_cli_command`
reproduces. An upgrade is not taken either: 0.4.0 is the newest release on PyPI and still
has the defect, so the workaround's job is to keep the reviewed pin valid. The workaround is
**self-neutralizing**: `model.to(device)` on a model already on `device` is a no-op, so a
future laya that moves the model before its first calibration pass makes the wrapper do
nothing; it can then be deleted with no other change. Applying it twice is also a no-op
(guard flag on the wrapper). Known gap, unchanged: the recorded `laya-train` CLI equivalent
still hits the defect on CUDA (the wrapper lives in our process; this stage never runs the
CLI).

**Evidence.** `tests/test_train_laya.py::test_the_calibration_patch_moves_the_model_first_and_wraps_once`
monkeypatches `laya.train.calibration_records` with a spy and records `.to` calls on a tiny
`torch.nn.Module`: the delegate must already see `.to(device)` applied (proved on cpu — no
CUDA needed), arguments are forwarded unchanged, and a second application must not
double-wrap. The bounded GPU smoke reused the earlier CPU smoke's fixture teacher set (14
rows, `laya_train.jsonl` sha `2b6a8b61…`) and micro settings — 1 epoch, `--max-len 512
--micro-batch 1 --grad-accum 1` — changing only the device:

| | CPU smoke (earlier, control) | GPU smoke (this workaround) |
|---|---|---|
| run | `p5-laya-ce-smoke-2026-10-08T143644+0000` | `p5-laya-ce-smoke-2026-10-08T145012+0000` (`kind=GPU_SMOKE`) |
| exit / walltime | 0 / 87.0 s | 0 / 20.2 s |
| device | cpu | cuda (`device cuda` in the training log) |
| epoch loss | [1.5400] | [2.0360] (finite; cpu and cuda runs are not bit-comparable) |
| peak VRAM (torch) | — (cpu) | 6162.2 MiB; nvidia-smi 6468 -> 13082 MiB over 11 samples, with the co-tenant P3 reader chain running |
| model hash | `2e00a143…`, stable across load | `aba24a4d…`, stable across load |

## D010 — P3 threshold selection: overall F1 behind both §10 constraints (2026-10-08)

**Defect.** D008's objective — among thresholds with at least one valid span, maximize
`f1_answerable + no_answer_accuracy` — is structurally abstention-biased, and degenerated on
the freshly trained medium reader (5,000 train questions; val_strict: 3107 answerable / 1292
impossible). The sum equals `1 + (f1_answerable - false_answer_rate)`, because
`no_answer_accuracy = 1 - false_answer_rate` on the disjoint impossible set: it can only
prefer answering when answerable F1 exceeds the false-answer rate, and it saturates at 1.0 as
the reader abstains. Medium sweep:

| threshold | answered answerable | f1_answerable | no_answer_accuracy | D008 sum | f1_overall |
|---|---|---|---|---|---|
| -4.5 (selected by D008) | 41/3107 | 0.0101 | 0.9907 | **1.0008** | 0.2981 |
| 0.0 | 2282/3107 | 0.4498 | 0.2957 | 0.7455 | 0.4045 |
| 0.5 (selected by D010) | 2475/3107 | 0.4757 | 0.2384 | 0.7141 | **0.4060** |

Every answering threshold scored below 1.0 while the near-abstain row at -4.5 scored above
it, so the run froze a reader answering 41 of 3107 answerable questions — the "answers
nothing" defect §8.6 flags, *produced by the selection objective itself*. The checkpoint was
fine: the same frozen reader scores f1_answerable 0.547 under forced decode. The spec never
mandated the sum: §4 says only "tune the threshold on strict validation"; §1 defines the
reader as a candidate generator; §8.6 lists BOTH degenerate extremes (answers nothing /
answers every negative) as defects to inspect before anything else.

**Rule.** `threshold_objective` = `f1_overall` (SQuAD2 convention: an impossible question is
scored against the empty reference, so a correct null contributes 1.0 and abstaining cannot
win the metric by itself); tie-break `em_overall`, then the lower threshold.
`acceptance_constraint_met` now requires BOTH §10 acceptance conditions at the chosen
threshold — at least one non-empty span with valid provenance, and at least one impossible
question returned null — and `selection_key` sorts feasible-first, so feasibility decides
before the objective. An infeasible sweep still raises and the run fails via the existing
SELECTION_FAILED path (D008's hard gate kept). The constraints remain load-bearing even under
overall F1: on a weak reader an all-null row still has the best raw `f1_overall` (correct
nulls score 1.0 — the smoke fixture's all-null point provably out-scores every spanning
threshold; constraint 1 excludes it), and a reader answering every negative has
`f1_overall = f1_answerable` (constraint 2 excludes it). D008's wounded-pilot concern is
resolved structurally instead of by the sum.

**Result.** `python -m src.pipeline.train_reader --profile medium --reselect` (new run
`p3-reader-medium-reselect-2026-10-08T152522+0000`, stage `P3_reader_reselect`) re-derived the
threshold of the frozen checkpoint without touching its weights. Selected threshold **0.5**:

- answered answerable 2475/3107 (f1_answerable 0.4757, em_answerable 0.2900);
- answered impossible 984/1292 (no_answer_accuracy 0.2384, false_answer_rate 0.7616);
- f1_overall 0.4060, em_overall 0.2748; 25 of the 33 thresholds feasible, and f1_overall is
  the max over the feasible set (runners-up 1.0 → 0.4057, 1.5 → 0.4052);
- infeasible rows: 7.5/8.0 (answer every negative) and -8.0..-5.5 (answer nothing);
- `constraint_binding: false` — on the trained reader the objective's own argmax is feasible,
  which is the D008 worry resolved rather than worked around.

`--reselect` loads the frozen checkpoint through the same `ReaderInference.load` contract
consumers use, re-runs the exact `_evaluate` val path (oracle sweep over all val rows,
retrieved-context metrics, both acceptance checks, predictions parquet, checksums) and
rewrites only the threshold-dependent artifacts (`reader_eval.json`, `reader_inference.json`,
`reader_predictions_val.parquet`, `model_card.md`, `checksums.json`) — never the weights,
tokenizer, or `training_args.json` (verified byte-identical after the run). The overfit gate
is read from the recorded `overfit_smoke.json`; it is never re-run or faked. A missing frozen
reader is refused cleanly with a FAILED registry row; `--force` and `--reselect` are mutually
exclusive. Fold readers (`train_correctness`) inherit the rule: an infeasible fold sweep is
recorded as a FAILED fold carrying the raise's message and the remaining folds continue; the
stage fails outright only when every fold is infeasible.

**Tests.** `tests/test_reader.py` + `tests/test_reader_pipeline.py` (updated for D010): the
all-null row still cannot win a feasible sweep; a sweep that never nulls an impossible
question is infeasible; a higher-`f1_overall` row wins even when an abstention-heavy row has
the higher D008 sum (built from the real medium rows at -4.5 and 0.5); ties break on
`em_overall` then the lower threshold; `selection_report` reports the new objective and key;
`require_acceptance` raises when the impossible-side check fails; the old +8 smoke grid
(answers every negative) now FAILS the run; and `--reselect` rewrites the threshold artifacts
while weights and `training_args.json` stay byte-identical, refusing cleanly without a frozen
reader. Full command: `pytest tests/test_reader.py tests/test_reader_pipeline.py
tests/test_correctness.py tests/test_baselines.py -q`: 72 passed.

## D011 — Retrieval cache: a scenario_id does not identify a corpus (2026-10-08)

**Defect.** The P2 ranking cache (`data/cache/retrieval/{split}_rankings_v1.jsonl`) reuses a
row when `scenario_id` matches and `retrieval_config_sha` is unchanged. Neither captures the
episode corpus: scenario sampling draws distractors from the *capped split's* document pool
(`src/data/scenarios.py` samples from `sorted(docs_by_id)`; the pool is the docs of the
capped rows, and `cap_rows` is a stratified subsample). So the same `qid` — hence the same
`scenario_id` — receives different distractors at different profile caps, while the retrieval
config hash (BM25/dense params only, `build_retrieval.retrieval_config_sha`) cannot see the
difference. The pilot's 300 rows were therefore served unchanged to the medium run. Measured
on the medium train cache: **300 of 4,999 rows have 12 of their 13 ranked documents outside
their scenario's corpus** (same on val: 300/4,399; the count equals the pilot cap, one row
per pilot scenario). The environment refused world-building — the first strict consumer —
with `ranking for tool 'bm25' references 12 doc(s) outside the episode corpus`, which is how
the defect surfaced; nothing had validated this invariant at the cache boundary.

**Blast radius (what had consumed the stale rows).** The poisoned cache was *quiet* for every
consumer that never checks corpus membership: the P3 state cache built at 16:07 was built
over it (states with out-of-corpus docs for the 300 questions), and the P3 medium reader's
retrieved-context val metrics / threshold selection had used it earlier. The oracle-context
reader metrics were unaffected.

**Fix (three guards, all at cache boundaries).**
1. *Fingerprint the corpus in the row.* `engine.scenario_corpus_sha(corpus_doc_ids)` is
   stored as `corpus_sha` in every ranking row (`to_row`/`from_row`), and `build_split`
   re-ranks any scenario whose row fingerprint differs — including every pre-fix row, which
   lacks the field, so the fix self-heals the existing cache. Rows for unchanged corpora are
   still reused across profiles (that reuse was the feature; only its key was wrong).
2. *Refuse to build a state cache from a ranking that steps outside the corpus.*
   `build_state_cache` raises with the scenario_id, tool and first offending doc instead of
   emitting states the environment must later reject.
3. *Refuse to roll out a stale state cache.* `worlds.build_worlds` compares the cache meta's
   recorded `sources` hashes (rankings/docs/questions/scenarios) against the current files
   and fails fast on any drift. `cache_reader._source_checksums` became public
   (`source_checksums`) and the P5 test fixture writes the block the way the real stage does.

**Rebuild chain (all re-run after this fix, in order).** P2 build_retrieval (re-ranks exactly
the drifted rows per split) → P3 cache_reader (state cache over the corrected rankings) →
P3 train_reader `--reselect` (the medium reader's val retrieved-context metrics and selected
threshold were computed over 300 stale val rankings; the frozen weights are untouched, only
threshold-dependent artifacts are rewritten) → P5 make_teacher (rebuilds; its fingerprint
covers the rankings and state cache SHAs) → downstream P5/P6/P7 as they run.

**Tests.** `test_a_cached_row_for_a_changed_corpus_is_rebuilt` (a same-id scenario with a
changed corpus is re-ranked; unchanged ones stay cache hits; rows carry `corpus_sha`),
`test_cache_reader_refuses_a_ranking_outside_the_corpus` (build fails with the D011 message),

## D012 — P1 corpora: hard negatives were configured but never implemented (v2, 2026-10-08)

**Finding (measured, not assumed).** After the D011 rebuild, the teacher's action
distribution looked degenerate: SEARCH_BM25=19, SEARCH_DENSE=10 of 34,993 train states
(ANSWER=10,913, ABSTAIN=24,051). The oracle was verified *correct*, not buggy: at the root
the bootstrap reveals `bm25[0]`, and episode `recall@1` is bm25 0.979 / dense 0.986 over the
13-doc corpora — for 1,563 of 4,999 train questions the gold document's candidate is already
correct at the root, and only 20 questions have a correct candidate reachable *exclusively*
through a search. Root labels decompose exactly: ABSTAIN 3,416 = 1,470 impossible + 1,946
answerable-without-any-correct-candidate; ANSWER 1,563; SEARCH 20; total 4,999. The corpora
were too easy, exactly the failure the spec predicts: "Nếu agent never SEARCH => bootstrap quá dễ
hoặc search reward/cost không cân đối" (`05_SEQUENTIAL_REINFORCE_TRAINING.md` §11).

**Defect.** `configs/base.yaml` has carried `data.hard_negative_ratio: 0.5` since the P1
commit, but `build_scenarios` never read it: 100% of distractors were uniform draws. Spec
`02_BM25_DENSE_RETRIEVAL.md` §6 requires the mix — "Nếu 8 distractors random quá dễ, tạo
`hard_distractors` chọn các đoạn có BM25/E5 similarity gần câu hỏi nhưng khác title ...
Trộn 50% random + 50% hard ... Record hardness distribution và phân tích curriculum" —
and "không dùng gold answer hoặc test performance để chọn".

**Fix (P1, D012).**
1. *Hard slots are question-side BM25 picks.* `build_scenarios` builds one reference
   `BM25Index` per split pool (the same `tokenize_vi` and `k1`/`b` as the P2 stage, passed
   from `cfg["retrieval"]["bm25"]`) and fills `round(hard_negative_ratio × n_distractors)`
   slots with the highest-scoring **other-title** pool documents for the *question text*.
   The gold answer, gold document identity (beyond the title exclusion) and test splits are
   never read for selection; the audit (`auditor.negative_signals`) already inspects every
   corpus document per negative, so hard distractors are false-negative-audited
   automatically.
2. *BM25-only, by decision.* The bootstrap tool is BM25, so bm25-hard negatives target the
   measured bottleneck; a reference E5 index would pull a GPU model into the deterministic
   data stage for no bearing on the root decision. Dense-side behavior stays an environment
   property to *measure* after the rebuild (dense `recall@1` may remain high — then
   SEARCH_DENSE is legitimately the valuable tool when BM25 top-1 is a hard distractor).
3. *Provenance.* `SCENARIO_VERSION = 2`; every scenario id and the RNG seed change
   (`stable_seed(qid, scenario_seed, version)`), so no cache can silently mix v1/v2 rows.
   `difficulty` records `n_distractors_hard`/`n_distractors_random`/`hard_mean_score`;
   `scenario_summary` aggregates the hardness distribution into the split manifest; the P1
   report and registry row record the ratio and the reference BM25 parameters.
4. *v1 is the `hard_negative_ratio=0.0` special case.* Verified at dev time against the
   pre-D012 module loaded from git: on the tiny fixture, ratio 0.0 + version 1 reproduces
   all three splits' corpora **bit-identically** (the RNG call sequence is unchanged).

**Rebuild chain.** P1 audit_split (v2 corpora, all splits) → P2 build_retrieval (all rows
re-ranked; corpus fingerprints changed) → P3 cache_reader → P3 train_reader `--reselect`
(val retrieved-context metrics and threshold depend on val corpora) → P5 make_teacher →
Laya CE/RLCD → P6/P7/P9. Acceptance signals to re-measure after rebuild: episode `recall@1`
(must drop from 0.979), questions with a deeper-only correct candidate (was 20/4,999),
SEARCH share of teacher labels (was 0.08%), and the audit's flagged-negative rate.

**Tests.** `tests/test_scenarios.py`: hard slots equal the independently computed top
BM25 other-title picks; the 0.5/1.0/0.0 ratios place the expected hard/random counts; corpora
are deterministic for a fixed pool/seed/version; changing the gold *answer* leaves the
corpus byte-identical (no label leak); the summary records the hardness distribution. Full
suite green (341 passed, 1 skipped).

## D014 — P2 cache: rows from superseded scenario versions are pruned, not kept (2026-10-09)

**Defect.** `build_retrieval` keys its cache by `scenario_id` and rebuilds a row only when the
*corpus fingerprint* differs (D011), but a scenario id embeds `SCENARIO_VERSION`
(`sc:{split}:{qid}:v{n}`). When D012 bumped the version to 2, the re-rank wrote the new v2
rows **next to** the dead v1 rows for the same qids instead of replacing them: measured
before the fix, `train_strict_rankings_v1.jsonl` held 9,998 rows = 4,999 v2 + 4,999 v1
(val 8,798 = 4,399+4,399; test 8,520 = 4,260+4,260). A superseded-version row can never be
served again — no current scenario asks for its id — so the file carried duplicate qids.

**How it surfaced.** `cache_reader.load_rankings` (the first consumer with a qid-unique
contract; the P3 state cache is keyed by qid) refused to build:
`ValueError: … train_strict_rankings_v1.jsonl: duplicate qid 'train:0005-0001-0004'`
(run `p3-reader-cache-medium-2026-10-09T003415+0000`, FAILED). The guard is correct and
stays. Nothing published was affected: no v2 state cache had been built, so no downstream
artifact consumed the duplicated file.

**Fix.** `_reusable_rows` now discards any row whose scenario id does not end in the current
version suffix and returns the count; `build_split` rewrites the file when rows were pruned
even if nothing needs re-ranking (the pruning must reach disk, not just memory). The
cross-profile reuse D011 introduced is preserved *within* a version — rows for scenarios
outside the current profile that already carry the current version stay in the file.

**Result (re-run `p2-retrieval-medium-2026-10-09T003754+0000`).** Pruned 4,999 / 4,399 /
4,260 rows (train/val/test), 0 rows re-ranked (all surviving rows cache hits), files now
hold exactly the current rows; report unchanged (union recall@5 0.9983, unreachable 0.0129),
which is the point — the pruning removed dead weight, not data.

**Tests.** `test_superseded_scenario_versions_are_pruned_from_the_cache` (an injected `:v0`
row is dropped, the file is rewritten without re-ranking, and the qid-unique contract
holds); the fixture now derives ids from `scenario_id_for` so it tracks the version constant.

## D016 — P6 selection step: the missing `best_selection.json` writer, multi-seed archives (2026-10-09)

**Context (defect).** Spec 02 §7 / 03 §5 require one config selected on val (primary: mean
episodic reward) and its checkpoint hash frozen in `outputs/manifests/best_selection.json`
BEFORE the strict test may be opened — `eval_baselines --split test_strict` refuses while the
file is absent and `report.py` proves the ordering in `docs/TEST_ACCESS_LOG.md`. No module
wrote that file ("Written by the P6 selection step" in `eval_baselines` referred to a step
that did not exist). Two more defects surfaced while designing it: (a) `train_rl` writes its
checkpoint to one fixed canonical dir (`outputs/models/rl_policy`) and its report/plots to
fixed paths, so running seeds 42/43/44 in sequence clobbers two of the three runs' evidence;
(b) `train_log.jsonl` is append-only (`append_jsonl`) against that shared dir, so a later
seed's log would contain an earlier seed's rows. The registry rows were also at risk: their
artifact hashes pointed at the canonical paths, which the next seed overwrites — stale hashes
that would make the `run_all` gate re-run P6 forever (the same defect class as D012/D014).

**Decision (reviewed via an independent opus consult, 2026-10-09; three corrections adopted).**

1. **`train_rl` archives every successful run** to `outputs/models/rl_runs/{run_id}/` — the
   whole canonical dir plus `summary/` (that run's report and both plots, which otherwise
   live at shared fixed paths). The registry row's artifacts point into the archive
   (immutable); the canonical dir is still written per run, as the spec's ``models/rl_policy``
   output. One-line companion fix: `train_log.jsonl` is cleared before a real run trains.
   Second companion fix, found by the suite after the archive landed: run ids carry a
   second-granularity timestamp, so two same-seed runs started in the same second produced
   the same run_id — the second run's `archive_run` crashed on the existing directory
   (FileExistsError, reproduced under load) and both attempts would have shared one id with
   two terminal registry rows, which `select_rl` reads as "expected 1". `train_rl.unique_run_id`
   now appends `-2`, `-3`… while the id is already present in the registry, so every attempt
   is a distinct, selectable run.
2. **New stage `P6_select`** (`src/pipeline/select_rl.py`). Pre-registered rule, fixed in code
   before any selection ran: **primary = highest `val_reward`** (mean episodic reward on
   val_strict, greedy, as the run's own post-`load_best` re-measurement — cross-checked
   against the registry row, never recomputed at select time); **tie-break = lowest seed**
   (derivable from frozen artifacts alone; no epsilon — a tolerance is a hidden hyperparameter).
   Eligibility = exactly one terminal `P6_rl` row, `SUCCEEDED`, this profile; `laya.regime`
   == `laya.frozen` (rlcd); retrieval sha, both splits' reader hashes, reward-spec hash and
   `eval_episodes` all equal to what the current config produces — an archive from a
   superseded chain can never be selected. Registry-vs-`config.json` disagreement, or an
   archive missing part of its evidence set, is corruption: RUNNING→FAILED row, no freeze.
3. **Install = clean swap, byte-identical**: stage `copytree(archive minus summary/)` under
   `.rl_policy.staging`, verify the four core files' sha256 against the winner's archive,
   replace the canonical dir, restore the winner's `summary/` files to the shared paths
   (every report citation then describes the selected run, not the last seed), and write the
   freeze **last** — a failure at any point leaves no new freeze. Freeze schema: rule +
   `created_utc` (registry-ts format) + `selected_update` (= winner's `best_update`, pinned by
   the report tests) + per-candidate rows (seed, run_id, val_reward, hashes) + `seed_summary`
   (mean/min/max) + `seeds_present`/`seeds_missing` vs the D015 budget [42, 43, 44] — the
   multi-seed mean ± range is first-class, never cherry-picked; a missing planned seed is
   warned and recorded, not hidden.
4. **Guards**: refuse while a `P6_rl` run's latest registry row is RUNNING (the registry is
   append-only, so a finished run keeps a historical RUNNING row — the check reads the latest
   row per run_id); refuse with exit 2 and **no registry row** when nothing is eligible;
   refuse to re-freeze after a `test_strict` P7 row unless `--force` (recorded as
   `forced: true`) — the one-shot-test door of spec 03 §5. Not added to the `run_all` DAG:
   the DAG cannot model the 3-seed budget, and auto-freezing after one seed would burn the
   one-shot test on partial evidence; the DAG's existing `needs_freeze` gate stays the
   enforcement.
5. **Reporting wiring**: `report.py` gains the `select_rl` stage row and REPRODUCE now names
   `python -m src.pipeline.select_rl` as the freeze command.

**Verification (measured, all in this repo).** New `tests/test_select_rl.py` (15 tests: rule,
tie-break order-independence, exclusion reasons, corruption without a freeze, refusals,
byte-identical rerun, real-toy-run integration asserting the canonical dir equals the winner
